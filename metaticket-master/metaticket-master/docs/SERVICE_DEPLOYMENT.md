# Deployment Guide - MetaTicket Kotlin Services

## Tổng quan

Các service Kotlin của MetaTicket được deploy thủ công bằng cách upload artifacts (libs + config) trực tiếp lên server. Mỗi service là một ứng dụng Ktor/Kotlin, được build bằng Gradle thành distribution package và quản lý vòng đời bằng systemd.

**Môi trường prod và staging được deploy trên hai server khác nhau.**

## Cấu trúc trên Server

### Đường dẫn theo môi trường

| Môi trường | Đường dẫn                                    | Server          |
|------------|----------------------------------------------|-----------------|
| Production | `/opt/metaticket/service/<tên service>`       | Production server |
| Staging    | `/staging/metaticket/service/<tên service>`   | Staging server  |

### Cấu trúc folder của mỗi service trên server

```
/opt/metaticket/service/<tên service>/
├── bin/
│   └── <tên service>          # Script khởi động (generated by Gradle)
├── lib/
│   ├── <tên service>-3.0.0.jar
│   ├── common-logger-1.0.0.jar
│   ├── ktor-server-core-*.jar
│   └── ... (tất cả dependency jars)
└── conf/                       # (nếu có config riêng ngoài classpath)
```

## Yêu cầu

- JDK 17+ đã cài trên server
- User `metaticket` và group `metaticket` đã tạo trên server
- SSH access đến server đích
- Gradle đã cài trên máy local (hoặc dùng gradlew)

## Quy trình Build

### Build một service cụ thể

```bash
cd d:\metaticket\source\metaticket\kotlin

# Build distribution cho service
./gradlew :service.<tên service>:distTar
```

Ví dụ:
```bash
./gradlew :service.authentication:distTar
```

Output sẽ nằm tại:
```
service.<tên service>/build/distributions/service.<tên service>-3.0.0.tar
```

### Build tất cả services

```bash
./gradlew distTar
```

## Quy trình Deploy

### 1. Build distribution

```bash
./gradlew :service.<tên service>:distTar
```

### 2. Upload lên server

```bash
# Staging
scp service.<tên service>/build/distributions/service.<tên service>-3.0.0.tar \
    user@<STAGING_SERVER>:/tmp/

# Production
scp service.<tên service>/build/distributions/service.<tên service>-3.0.0.tar \
    user@<PROD_SERVER>:/tmp/
```

### 3. SSH vào server và deploy

```bash
ssh user@<SERVER>

# Dừng service
sudo systemctl stop metaticket-<tên service>

# Giải nén distribution
cd /tmp
tar -xf service.<tên service>-3.0.0.tar

# Copy libs vào đúng vị trí (ví dụ staging)
sudo cp -r service.<tên service>-3.0.0/lib/* /staging/metaticket/service/<tên service>/lib/

# Copy config tương ứng với môi trường
```

### 4. Upload config (nếu có thay đổi)

```bash
scp service.<tên service>/conf/* user@<STAGING_SERVER>:/staging/metaticket/service/<tên service>/lib/
```

### 5. Chuyển ownership

```bash
# Staging
sudo chown -R metaticket:metaticket /staging/metaticket/service/<tên service>/

# Production
sudo chown -R metaticket:metaticket /opt/metaticket/service/<tên service>/
```

> ⚠️ **QUAN TRỌNG:** Mọi file upload lên PHẢI chuyển owner sang `metaticket:metaticket`. Nếu không, service sẽ không có quyền đọc/ghi và sẽ lỗi khi khởi động.

### 6. Khởi động lại service

```bash
sudo systemctl start metaticket-<tên service>

# Kiểm tra trạng thái
sudo systemctl status metaticket-<tên service>

# Xem logs
sudo journalctl -u metaticket-<tên service> -f
```

## Quản lý Systemd

### Vị trí file systemd

Các file service unit được đặt tại folder mặc định của systemd:

```
/etc/systemd/system/metaticket-<tên service>.service
```

### Mẫu file systemd service

```ini
[Unit]
Description=MetaTicket <Tên Service>
After=network.target

[Service]
Type=simple
User=metaticket
Group=metaticket
WorkingDirectory=/opt/metaticket/service/<tên service>
ExecStart=/opt/metaticket/service/<tên service>/bin/service.<tên service>
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

### Các lệnh systemd thường dùng

```bash
# Khởi động service
sudo systemctl start metaticket-<tên service>

# Dừng service
sudo systemctl stop metaticket-<tên service>

# Restart service
sudo systemctl restart metaticket-<tên service>

# Kiểm tra trạng thái
sudo systemctl status metaticket-<tên service>

# Bật auto-start khi server boot
sudo systemctl enable metaticket-<tên service>

# Tắt auto-start
sudo systemctl disable metaticket-<tên service>

# Xem logs real-time
sudo journalctl -u metaticket-<tên service> -f

# Xem logs gần đây (100 dòng cuối)
sudo journalctl -u metaticket-<tên service> -n 100

# Reload systemd sau khi sửa file .service
sudo systemctl daemon-reload
```

## Service News (Spring Boot)

`service.news` dùng Spring Boot (không phải Ktor). Quy trình upload/systemd giống các service khác; khác ở lệnh build và profile.

### Build

```bash
./gradlew :service.news:bootDistTar
# Output: service.news/build/distributions/service.news-boot-3.0.0.tar
```

(Không dùng `distTar` thin của application plugin — dùng **`bootDistTar`** để có fat jar + `bin/service.news`.)

### Deploy

Giải nén `service.news-boot-3.0.0.tar` rồi đổi tên folder thành `service.news` tại:

- Staging: `/staging/metaticket/service/service.news/`
- Prod: `/opt/metaticket/service/service.news/`

Copy mẫu:

- `service.news/conf-sample/metaticket-service.news.staging.service` → `/etc/systemd/system/metaticket-service.news.service` (staging)
- `service.news/conf-sample/metaticket-service.news.service` → prod
- `service.news/conf-sample/service.news.env` → `/etc/metaticket/service.news.env` (điền secret)

Listen port đã khớp nginx upstream `news_service`:

- Staging: **4041** (`SPRING_PROFILES_ACTIVE=staging`)
- Prod: **3041** (`SPRING_PROFILES_ACTIVE=prod`)

Private API qua admin nginx (`auth_request` trên `/private/`). Public API: `/api/public/news/`.

WordPress CMS: `metaticket-wordpress/docs/STAGING_DEPLOY.md`.

## Service Notification (đặc biệt)

Service notification có kiến trúc plugin-based. Các plugin jars được đặt riêng trong folder `plugin/` trên server (không nằm chung trong `lib/`).

### Cấu trúc trên server

```
/opt/metaticket/service/service.notification/
├── bin/
│   └── service.notification
├── lib/
│   ├── service.notification-3.0.0.jar
│   └── ... (dependency jars)
└── plugin/
    ├── mail_template/
    │   ├── plugin.mailtemplate.basic-*.jar
    │   ├── plugin.mailtemplate.offline_payment-*.jar
    │   ├── plugin.mailtemplate.otp-*.jar
    │   ├── plugin.mailtemplate.qrcode-*.jar
    │   └── plugin.mailtemplate.ticketslots-*.jar
    └── zns_template/
        ├── plugin.zns-*.jar
        └── plugin.zns.basic-*.jar
```

### Deploy plugin

Khi thêm/cập nhật plugin, copy jar tương ứng vào đúng subfolder:

```bash
# Mail template plugins
sudo cp plugin.mailtemplate.basic-*.jar /opt/metaticket/service/service.notification/plugin/mail_template/

# ZNS plugins
sudo cp plugin.zns.basic-*.jar /opt/metaticket/service/service.notification/plugin/zns_template/

# Chuyển ownership
sudo chown -R metaticket:metaticket /opt/metaticket/service/service.notification/plugin/
```

Sau khi cập nhật plugin, cần restart service notification để load plugin mới.

## Deploy nhanh (Script tham khảo)

Dưới đây là script mẫu để deploy nhanh một service lên staging:

```bash
#!/bin/bash
SERVICE_NAME=$1
SERVER="user@<STAGING_SERVER>"
DEPLOY_PATH="/staging/metaticket/service/${SERVICE_NAME}"

if [ -z "$SERVICE_NAME" ]; then
    echo "Usage: ./deploy.sh <service-name>"
    echo "Example: ./deploy.sh service.authentication"
    exit 1
fi

echo "=== Building ${SERVICE_NAME} ==="
./gradlew :${SERVICE_NAME}:distTar

echo "=== Uploading to server ==="
scp ${SERVICE_NAME}/build/distributions/${SERVICE_NAME}-3.0.0.tar ${SERVER}:/tmp/

echo "=== Deploying on server ==="
ssh ${SERVER} << EOF
    sudo systemctl stop metaticket-${SERVICE_NAME}
    cd /tmp
    rm -rf ${SERVICE_NAME}-3.0.0
    tar -xf ${SERVICE_NAME}-3.0.0.tar
    sudo rm -rf ${DEPLOY_PATH}/lib/*
    sudo cp -r ${SERVICE_NAME}-3.0.0/lib/* ${DEPLOY_PATH}/lib/
    sudo cp -r ${SERVICE_NAME}-3.0.0/bin/* ${DEPLOY_PATH}/bin/
    sudo chown -R metaticket:metaticket ${DEPLOY_PATH}/
    sudo systemctl start metaticket-${SERVICE_NAME}
    sudo systemctl status metaticket-${SERVICE_NAME}
    rm -rf /tmp/${SERVICE_NAME}-3.0.0*
EOF

echo "=== Done ==="
```

## Lưu ý quan trọng

1. **Ownership:** Tất cả file PHẢI thuộc `metaticket:metaticket`. Quên chuyển ownership là nguyên nhân phổ biến nhất khiến service không start được.

2. **Dừng service trước khi deploy:** Luôn `systemctl stop` trước khi copy file mới để tránh lỗi file lock hoặc inconsistent state.

3. **Config không nằm trong distribution:** File `conf/` KHÔNG được tự động đóng gói vào distribution tar. Cần copy riêng lên server khi config thay đổi.

4. **Kiểm tra sau deploy:** Luôn kiểm tra `systemctl status` và `journalctl` sau khi start để đảm bảo service chạy bình thường.

5. **Backup trước khi deploy production:** Nên backup folder `lib/` và `conf/` hiện tại trước khi deploy version mới trên production:
   ```bash
   sudo cp -r /opt/metaticket/service/<tên service>/lib /opt/metaticket/service/<tên service>/backup/<date-time>
   ```

6. **JDK version:** Tất cả services yêu cầu JDK 17. Kiểm tra `java -version` trên server.

7. **Port conflict:** Mỗi service chạy trên một port riêng (cấu hình trong `application.conf`). Đảm bảo không trùng port giữa các service.

8. **Hai server khác nhau:** Staging và Production deploy trên hai server khác nhau, nên không lo port conflict giữa hai môi trường.
